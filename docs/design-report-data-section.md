# 지속가능경영보고서 데이터 장 읽기 — 설계 초안

> 2026-09-22 초안 · 2026-09-24 L0 구현 · 근거: 시총 상위 30개사 실행 기록 + 표본 3개 보고서 프로토타입
>
> **진행:** L0(기반 고치기)·L2(표 행 후보, `sustainability_report_data`)·연도 잇기(`esg_timeseries`)가 구현됐다 — 결과는 [실측 노트 19·20·21·22](anecdotes.md).
> 2절의 원칙 변경은 2026-09-24 승인되어 CLAUDE.md 규칙 14 가 됐다. L1(쪽 지도 노출)·L3(지표로 찾기)은 초안이다.

## 0. 한 줄

보고서 뒤쪽 **데이터 장이 몇 쪽부터 몇 쪽인지 먼저 알려 주고**, 그 쪽의 표를
「행 이름 × 열 머리(연도·경계) × 단위 × 각주」로 펼친 **후보**를 준다.
**검사를 모두 통과한 칸만 값으로 싣고**, 나머지는 그 표 블록의 원문 조각을 넘긴다.
「보고서 값 = N」 같은 확정 필드는 만들지 않는다.

## 1. 왜 — 30개사 실행에서 막힌 곳 (2026-09-22)

5개 작업이 6개사씩 동시에 `sustainability_report_text` 를 불렀다(쪽 읽기 133회, 찾기 108회).

| 증상 | 횟수 | 원인 |
|---|---:|---|
| 쪽을 열 정렬 없이 평문으로 받음 | 100 / 133 | R1 |
| 쪽 본문 6,000자에서 잘림 | 21 | R3 |
| 찾기 결과가 8쪽 상한을 넘어 발췌가 잘림 | 16 | R4 |
| 찾기 0건(표기 차이) | 16 | R4 |
| 5개 작업이 같은 시각에 시간 초과 → 전원 멈춤 | 1회 | R2(추정) |

- **R1 PDF 원본을 한 건만 들고 있음.** 「찾기 → 그 쪽 정렬해 보기」에는 원본이 필요한데, 서버는 가장 최근 한 건만 10분 들고 있다.
  동시 호출이 서로 밀어내서, 25MB 이하 문서도 「문서가 커서 평문으로 보여줍니다」가 떴다.
  - 크기를 확인한 21건은 모두 24.6MB 이하였다.
  - 7건은 KIND 가 크기 조회를 거부해 확인하지 못했다.
  - 안내 문구도 원인을 잘못 말한다.
- **R2 PDF 해석이 서버의 요청 처리 흐름 안에서 그대로 돈다.** `load_pages`·`page_layout` 이 비동기 처리 안에서 동기로 실행된다.
  무거운 문서 하나가 파싱되는 동안 다른 요청이 모두 기다린다.
  - 코드상 사실이다(스레드로 넘기는 곳이 없었다). 작은 재현(5개 작업 × 2사)에서 루프가 최대 1.36초 멈췄다.
  - 그것이 30개사 실행의 동시 멈춤 원인이라는 것은 여전히 추정이다.
- **R3 정렬 텍스트는 공백이 많다.** 데이터 쪽은 한 쪽이 6,000자를 쉽게 넘는다.
- **R4 데이터 장이 어디인지 모른다.** 찾기가 본문 서술 쪽까지 걸려서 정작 표가 있는 쪽이 8쪽 상한 밖으로 밀린다.
- **R5 연도 열 대응을 매번 읽는 AI가 손으로 한다.** 평문에서는 「어느 숫자가 2025년 열인가」를 순서로 추측해야 했다.
  (예: 삼성생명 표는 2022·2023·2024성과·2024목표·2025성과·2025목표의 여섯 열이었다.)

데이터가 있는 곳(원문을 연 28개사): 뒤쪽 데이터 장 23 · 본문 장에 흩어짐 2 · 별도 파일 3.
데이터 장 이름은 ESG Data / Factbook / Facts & Figures / 부록 / Data Pack.
위치는 전체 쪽수의 66~93% 구간이고, 대부분 75~88%다.

## 2. 저장소 원칙과의 관계 — **바꾸는 제안이다**

현재 open-esg-korea 원칙 두 곳과 부딪힌다.

- **규칙 8:** 「보고서에서 수치를 뽑아 필드로 만들지 않는다」.
- **범위 밖 목록:** 「보고서 표의 수치 자동 추출」.

그래서 경계를 이렇게 긋는다.

- **필드가 아니라 후보다.** 값마다 쪽·표 제목·행 이름·열 머리·단위·각주·검사 결과를 붙인다.
  한 보고서에 같은 지표 값이 여럿이면(국내/글로벌, 시장/지역기반) **전부** 후보로 준다. 어느 것을 쓸지는 읽는 쪽이 정한다.
- **조용히 틀린 값 금지.** 검사를 하나라도 통과하지 못한 행은 값을 싣지 않고 「원문 조각」으로 강등한다.
  커버리지보다 **조용한 오답 0** 이 먼저다.
- **원본 PDF 비저장 유지.** 남기는 것은 쪽 텍스트와 글자 좌표에서 떠낸 가벼운 파생물뿐이다.

## 3. 구성 — 네 층

### L0 기반 고치기 (R1·R2·R3) — ✅ 2026-09-24 구현

1. **파싱을 스레드로.** `asyncio.to_thread` 로 넘기고, 동시 파싱 수를 2개로 묶는다(세마포어).
   한 문서가 무거워도 다른 요청이 멈추지 않게 한다.
2. **원본 한 칸 대신, 데이터 장 쪽의 파생물을 캐시.** 처음 받을 때 L1 의 핵심(`extract.data_section`)으로 데이터 장을 찾는다.
   그 쪽들의 정렬 텍스트(문서당 수십~100KB)를 그 자리에서 떠 두고 원본은 버린다. 글자 좌표는 L2 때 더한다.
   - 이렇게 하면 「찾기 → 보기」가 동시 호출에 흔들리지 않는다.
   - 데이터 장 밖의 쪽을 정렬해서 볼 때만 다시 받는다.
3. **평문으로 내려간 이유를 사실대로 말한다.** 크기 초과 / 캐시에서 밀림 / 정렬 실패를 구분한다.
4. **쪽 보기를 넓힌다.** 줄 끝·공통 왼쪽 여백·이어진 빈 줄만 걷어 열 경계를 유지한다(`compact_layout`). `page="136-140"` 처럼 쪽 범위(최대 5쪽)를 허용한다.
5. **(재현 중 발견) KIND 캐시 상한을 개수에서 글자 수로.** 8건 상한이 회사마다 두 건씩 쓰는 작은 서식을 밀어내 호출마다 KIND 를 4.8번 불렀다 → 1.8번.

**결과(작은 재현, 5개 작업 × 2사, MCP 도구 계층):** 평문으로 나간 쪽 24/30 → 1/50 · 루프 최대 멈춤 1.36초 → 0.21초 · 호출당 KIND 요청 4.8 → 1.8.
남은 1쪽은 30MB 문서의 데이터 장 밖 쪽이고, 이유를 사실대로 말한다.

### L1 데이터 장 찾기 (쪽 지도)

이미 캐시에 있는 평문만 쓰므로 추가 비용이 없다.

- **쪽마다 신호를 센다.**
  - 쉼표가 든 숫자의 수
  - 연도 3개 연속 머리(2023 2024 2025)
  - 단위 토큰(tCO2e·MWh·TJ·톤·㎥·%·명)
  - 대조표 코드(GRI 305-1, TC-SC-140a.1 등)
  - 검증의견서 문구
- **구간을 정한다.** 숫자 밀도와 연도 머리 기준을 넘는 쪽들 중 가장 긴 연속 구간(틈 2쪽 허용)을 데이터 장으로 본다.
  대조표 쪽과 검증의견서 쪽은 따로 표시한다. 검증의견서는 Scope 1·2 합계를 다시 싣는 **교차 확인의 닻**이다.
- **쪽마다 주제 표지를 붙인다.** 온실가스·에너지·용수·폐기물·임직원·안전 등이다. 동의어 사전은 한 곳에만 둔다(`krx/codes.py` 방식).
- **첨부를 고른다.** 첨부가 여럿이면 데이터 모음집(이름에 Data·데이터·Factbook)을 따로 표시한다.
  - 지금은 국문 첫 파일만 고른다.
  - 신한지주는 첨부 자체가 Data Pack 이었다.
- **데이터 장이 없을 때.** 본문의 「별도 발간 데이터북 / ESG Factbook」 문구를 찾아 그 쪽을 짚어 준다(KB금융·삼성바이오로직스).
  「데이터 없음」이라고 답하지 않는다.

### L2 표 행 후보

pdfplumber 글자 좌표(`extract_words`)로 한 쪽을 다음 순서로 푼다.

1. **줄:** 글자 위치의 세로 좌표로 묶는다.
2. **열:** **숫자의 오른쪽 끝**이 모인 자리다(숫자는 오른쪽 정렬). 머리글 위치로 열을 잡으면 두 줄 머리에서 실패한다(프로토타입 v1).
3. **열 머리:** 열 위의 연도 줄과 그 아래 하위 머리 줄(국내/해외/합계, DX/DS, 별도/자회사)에서 가장 가까운 것을 붙인다.
   연도 하나가 두 열 위에 걸치면, 이웃 연도와의 중점까지를 그 연도의 몫으로 본다.
4. **표 블록:** 열 사이에 라벨 글자(한글·영문)가 끼어 있으면 거기서 표를 가른다. 좌우로 붙은 두 표를 떼어 내는 규칙이다.
5. **행:** 라벨 + 단위 + 열별 값.
   - 각주 표지 `1)`·`2)` 는 숫자가 아니라 표지로 읽는다.
   - 표지는 행에 달고, 표 아래 각주 문장을 연결한다. 경계 단서는 각주에 있다(실측 노트 14).
6. **표 제목:** 머리 위 가장 가까운 줄.

**행마다 검사 — 모두 통과해야 값(`aligned`), 아니면 `needs_reading` + 그 블록의 원문 조각:**

| 검사 | 무엇을 막나 |
|---|---|
| 토큰 대조(기존 `suspect_cells`) | 열을 잘못 잘라 쪼개진 숫자 |
| 열 수 일치 | 빈 칸·밀린 칸 |
| 머리 완결(연도 + 하위 머리가 있으면 둘 다) | 부문 값이 전사 값처럼 보이는 것 |
| 떠돈 값 0(블록 안 숫자가 모두 어느 열엔가 붙음) | 옆 표 숫자가 섞인 것 |
| 합계 검산(합계·계·총 행 = 부분 행의 합, 반올림 허용) | 행이 한 칸씩 밀린 것 |
| 닻 일치(GIR 명세서·검증의견서의 같은 수) — 통과 조건 아님, 가점 표시 | — |

**프로토타입 결과 (6개 쪽):**

| 쪽 | 표 모양 | 결과 |
|---|---|---|
| 삼성전자 p70 | 좌우로 붙은 두 표, 머리 한 줄 | 두 표 모두 전 행 정렬. 실측 노트 11(두 표가 섞임)의 사례를 가름 |
| 삼성전자 p72 에너지 | 부문(DX/DS) × 연도, 두 줄 머리 | 6열 모두 정렬 |
| 삼성전자 p71 | 왼쪽 폐기물·오른쪽 수자원 | 주요 행 값은 맞음. 오른쪽 표 숫자가 섞여 경고 |
| 현대모비스 p137 | 별도/국내자회사/해외자회사/합계 × 연도 | 대부분 정렬. 「국내 자회사」가 「자회사」로 쪼개져 한 열이 겹침(경고) |
| 삼성전자 p72 온실가스 | 좌우 두 표 + 두 줄 머리 | **위험 사례.** 각주 표지 `2)` 를 숫자로 읽어 하위 머리를 놓침. DX부문 값이 부문 표시 없이 연도 값처럼 나옴. 행 경고는 붙었지만 칸 값은 그럴듯해 보인다 |
| LG에너지솔루션 p141 | 국내/해외/전사 × 연도, TJ·MWh 두 줄 한 쌍, 라벨과 숫자가 다른 줄 | 실패(경고) |

위험 사례 때문에 두 규칙을 **통과 조건**으로 못 박는다.
- 각주 표지는 숫자에서 뺀다.
- 머리 완결 검사를 통과해야만 `aligned` 가 된다.

### L3 지표로 찾기 (선택)

- **지표 이름으로 찾기:** `metric="ghg_s12|energy|water|waste|female_ratio"` 를 받는다.
  동의어 사전으로 **데이터 장 안에서만** 찾고, L2 행 후보를 돌려준다.
- **단위 환산은 제안만:** 환산 계수(GWh×3.6 → TJ, 1 TOE = 0.041868 TJ)를 붙인다.
  보고서가 전력을 1차에너지(9.6 GJ/MWh)로 환산했는지는 각주 문구와 GIR 국내값 일치 여부로 감지해 표시한다.
  30개사 표에서 13개사가 이 기준이라 회사 간 에너지 비교가 최대 2.7배 흔들렸다.
- **기존 온실가스 대조와 연결:** `ghg_emissions(report=True)` 의 발췌를 L2 행 후보로 바꿔, 범위 축(경계·Scope 2 기준·NF3)을 열 머리·각주에서 읽는다.

## 4. 도구 표면 — 정할 것

- **A. 기존 `sustainability_report_text` 확장:**
  - 쪽 지도: `section="data"`
  - 행 후보: `rows=True`
  - 쪽 범위: `page="a-b"`
  - 도구 수를 늘리지 않고 설명만 넓힌다.
- **B. 새 도구 `report_data(company, metric|find, year)`:** 「숫자를 달라」는 질문에서 찾기 쉽다. 도구 설명이 짧게 유지된다.

**권고: A로 시작(L0~L2), L3 에서 B를 검토.** 행 후보는 결국 「그 쪽을 보는 다른 방식」이라 같은 도구 안에 두는 편이 설명이 덜 갈린다.

## 5. 검증 계획

- **정답집:** 오늘 30개사 결과(28사 × 5지표, 쪽 번호·경계·원문 값 포함, 150행). 주의할 점이 셋이다.
  - **같은 오류를 공유할 수 있다.** 같은 평문을 읽은 AI가 만든 값이라 이번 도구와 오류를 공유할 수 있다(정답이 독립적이지 않다).
  - **독립 표시:** GIR 명세서·검증의견서와 일치하는 값은 「독립 닻」으로 따로 표시한다.
  - **사람 확인:** 20개 표본은 사람이 PDF 로 직접 확인한다.
- **지표와 목표:**

| 지표 | 목표 |
|---|---|
| 데이터 장 재현율(정답 쪽이 찾은 구간 안에 있는 비율) | 27/28 이상 |
| `aligned` 로 낸 값 중 틀린 것(조용한 오답) | 0 |
| `aligned` 비율(커버리지) | 목표 없이 기록만 — 오답 0 을 지킨 뒤 늘린다 |
| 동시 5개 작업에서 평문 강등률 | 0 (지금 75%) |
| 동시 5개 작업에서 전원 시간 초과 | 0 |

- **테스트(network 0):** PDF 원본 대신 **쪽별 글자 좌표 JSON**(쪽당 수십 KB)을 fixture 로 둔다. 원본 PDF(4~25MB)를 저장소에 넣지 않는다.

## 7. 알려진 난제

- **라벨과 숫자가 다른 줄:** LG에너지솔루션 p141 은 「전력 사용량 4)」 다음 줄에 숫자가 온다 → 이름 줄 배정 규칙(에너지 단위 쌍 · 이름이 같은 줄인 행에서 번지기 · 방향 엇갈림은 검사)으로 풀었다. 한글만 아래 줄로 읽히던 것은 표 모양이 아니라 깨진 글꼴 탓이었다(노트 22).
- **단위가 번갈아 나오는 행:** TJ 줄과 MWh 줄이 한 쌍이다 → 단위 열을 행 키에 넣는다.
- **머리 단어 쪼개짐:** 「국내 자회사」가 「자회사」로 쪼개진다 → 하위 머리 줄의 이웃 단어를 합친다.
- **본문 장에 흩어진 표:** 삼성화재·HD현대일렉트릭은 L1 구간 밖이다 → 주제 표지로 본문 쪽도 후보에 올린다.
- **이미지로 된 표:** OCR 은 하지 않는다(범위 밖 유지). 「못 읽었다」고 말한다.
